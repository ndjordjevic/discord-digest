## Top topics

### Proposed new 68080 move, clr and extend instructions (move.Q/Octa, movs, movz, moveX)
biggun68080 listed candidate instructions including move.Q/Octa, sign/zero-extending moves and endian-swapping moveX; tommo8871 and tjomp liked them, and biggun68080 floated clr.q/clr.octa and move.count for tail bytes.

- move.octa does a 128-bit read and write in 2 cycles, about 1600 MB/s, with a possible 3000 MB/s peak using both EAs in parallel.
- move.count with a register count copies 16 bytes but writes only the count, handling the 1-15 leftover bytes in one instruction.
- tjomp says the fastest copy today is 4x load/4x store unrolled; an EA-to-EA move using no register would be a big win.

❓ **Open:** A one-instruction counted copy (move16.count with auto-decrement) is blocked by pipelining, since the counter is owned by the ALU; biggun68080 will keep it in mind.

### Masked move16/move8 for sprite copying; move8 mask requested for odd widths
angelofspectral asked for a move8 mask alongside move16 mask for sprite widths like 20 or 24 pixels; tjomp supported it, and biggun68080 explained the byte-mask semantics.

- In byte mode each byte is compared to $00 and only non-zero bytes are written, so colour 0 stays transparent; replaces an 81-instruction loop.
- biggun68080 estimates the equivalent loop could take over 200 cycles on the 68060 because of mispredicted branches.
- Suggested alternatives: pad sprites to 16 bytes (rudi09421), or use AMMX pcmpeqb/por/bsel (tjomp); biggun68080 notes this fails for OS functions.
